# ADR-010 — Use AWS Amplify Hosting for the public frontend

## Status

Accepted for v0.5.

---

## Context

Family Learning Games v0.1 through v0.4 executes the frontend using a local Next.js development/build environment while the backend is already hosted in AWS.

The architecture currently resembles:

```text
Local Browser
     │
     ▼
localhost:3000
     │
     ▼
API Gateway HTTP API
     │
     ▼
Lambda
   ┌─┴─────────────┐
   ▼               ▼
DynamoDB       Amazon Bedrock
```

v0.5 corresponds to:

```text
FASE 5 — Desplegar públicamente en AWS
```

The application must therefore become accessible from the Internet without requiring users to run a local Next.js server.

The hosting solution should preserve the existing architectural principles:

* Next.js remains the frontend framework.
* Backend remains independently deployed.
* Frontend communicates with backend through HTTP APIs.
* Domain and Application remain infrastructure-independent.
* Operational complexity should remain low.
* Cost should remain appropriate for a small personal project.
* Deployment should integrate naturally with the Git repository.

Potential alternatives include:

```text
AWS Amplify Hosting

Amazon S3 + CloudFront

Custom CloudFront + Lambda/compute architecture

Container hosting

EC2
```

Managing CloudFront/S3 or compute infrastructure directly would introduce infrastructure that is not currently required by the product.

---

## Decision

Use:

```text
AWS Amplify Hosting
```

as the public hosting platform for the Family Learning Games Next.js frontend.

Target architecture:

```text
GitHub
   │
   ▼
AWS Amplify Hosting
   │
   │ HTTPS
   ▼
Browser
   │
   │ HTTPS
   ▼
API Gateway HTTP API
   │
   ▼
Lambda
   │
   ├──► DynamoDB
   │
   └──► Amazon Bedrock
```

AWS Amplify Hosting is responsible only for hosting and deploying the frontend.

It does not become the application backend.

The existing backend architecture remains:

```text
API Gateway
    │
    ▼
Lambda
    │
    ▼
Application
   ┌┴─────────────┐
   ▼              ▼
Repository   GameGenerator
   │              │
   ▼              ▼
DynamoDB       Bedrock
```

---

## Frontend configuration

The backend URL must remain externally configurable.

Example:

```text
NEXT_PUBLIC_GAME_API_BASE_URL
```

The value is configured for the deployed frontend environment.

Application code must not contain an environment-specific API Gateway URL.

---

## CORS

The public Amplify origin must be added to the API's allowed origins.

Conceptually:

```text
AllowedOrigins:
  - http://localhost:3000
  - https://<amplify-host>
```

Local development support will therefore remain available.

---

## Deployment model

The expected deployment flow is:

```text
Developer
    │
    │ git push
    ▼
GitHub
    │
    ▼
Amplify build
    │
    ▼
Amplify deploy
    │
    ▼
Public HTTPS application
```

For v0.5 a simple branch-to-environment deployment is sufficient.

No sophisticated environment promotion pipeline is required.

---

## Domain

Use the Amplify-managed domain for v0.5.

Example:

```text
https://main.xxxxx.amplifyapp.com
```

A custom domain is intentionally not required to complete v0.5.

It can be introduced independently later without altering Domain or Application architecture.

---

## Authentication

Making the application publicly reachable does **not** imply introducing authentication in v0.5.

Do not add Cognito solely because the frontend becomes public.

Authentication and family profiles belong to a later product capability.

---

## Consequences

### Positive

#### Low operational overhead

There is no need to manually manage:

```text
web servers
EC2
containers
load balancers
CloudFront distributions
frontend deployment servers
```

for this version.

---

#### Git-based deployment

Frontend deployment can follow normal source-control workflow.

```text
commit
  ↓
push
  ↓
build
  ↓
deploy
```

---

#### HTTPS

The publicly exposed frontend uses HTTPS.

---

#### Architecture remains decoupled

The frontend continues to depend only on the HTTP API contract.

```text
Frontend
    │
    ▼
HTTP API
```

and not on Lambda, DynamoDB or Bedrock implementations.

---

#### Incremental evolution

The change required by v0.5 remains small.

```text
v0.4

localhost
   │
   ▼
AWS backend


v0.5

Amplify
   │
   ▼
AWS backend
```

---

## Negative consequences

### Additional AWS service

Amplify Hosting becomes another AWS-managed service used by the project.

---

### Hosting-specific configuration

Build and environment configuration must be maintained for the Amplify deployment.

---

### CORS becomes environment-aware

The backend must recognize the production/public frontend origin in addition to localhost.

---

### Framework compatibility must be verified

The Next.js version used by the application must be compatible with the versions supported by Amplify Hosting.

This should be validated during implementation and when upgrading Next.js.

---

## Alternatives considered

### Amazon S3 + CloudFront

Advantages:

```text
simple
highly scalable
low cost
```

However, it requires more explicit hosting/CDN configuration and can impose constraints depending on which Next.js runtime features are used.

Rejected for v0.5 because Amplify provides a simpler Next.js-oriented deployment path.

---

### EC2

Would require management of:

```text
instances
operating system
Node.js runtime
patching
deployment
network exposure
availability
```

Rejected because the operational complexity is unjustified.

---

### ECS/Fargate

Would require:

```text
container image
ECR
ECS
task definitions
networking
potential load balancing
```

Rejected because container orchestration provides no meaningful benefit to the current product.

---

### Deploy frontend inside the existing backend Lambda

Rejected because it would mix independent responsibilities:

```text
frontend hosting
+
application API
```

and unnecessarily couple deployment lifecycles.

---

## Cost consideration

v0.5 favors usage-based managed services.

The architecture continues to avoid permanently running servers.

The project owner should periodically review AWS billing and resource usage as public traffic becomes possible.

---

## Security consideration

No AWS credentials or private secrets may be shipped to the browser.

Values exposed through:

```text
NEXT_PUBLIC_*
```

must be considered public.

The browser communicates with AWS backend capabilities exclusively through the exposed HTTP API.

---

## Scope boundary

ADR-010 does not decide:

```text
family authentication
user accounts
Cognito
PWA
custom domain
audio
images
multiplayer
multiple production environments
```

Those decisions will be addressed by future versions when required.

---

## Result

After implementing this ADR:

```text
                     INTERNET

                        │
                        ▼
                Amplify Hosting
                        │
                        ▼
                  Next.js App
                        │
                        ▼
                API Gateway HTTP
                        │
                        ▼
                     Lambda
                   ┌────┴────┐
                   ▼         ▼
               DynamoDB    Bedrock
```

Family Learning Games becomes publicly accessible while retaining the serverless and decoupled architecture established in previous versions.
