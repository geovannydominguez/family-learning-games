# Family Learning Games — Requirements v0.6

## 1. Version goal

Version **v0.6** introduces persistent family player profiles.

The goal is to evolve the existing `Player` concept from static or local configuration into a persistent application entity that can be selected when creating or playing games.

Player profiles provide the minimum context required to personalize game generation and gameplay, especially the player's age.

v0.6 must preserve the architecture and capabilities delivered in previous versions:

* v0.1 — Local playable frontend
* v0.2 — Serverless AWS backend
* v0.3 — DynamoDB persistence
* v0.4 — AI-generated games with Amazon Bedrock
* v0.5 — Public AWS deployment

v0.6 must not introduce unrelated capabilities planned for future phases.

---

# 2. Functional requirements

## FR-01 — Persistent player profiles

The application must persist player profiles independently of games and game sessions.

Each player must have at least:

```ts
interface Player {
  playerId: string;
  name: string;
  age: number;
  createdAt: string;
  updatedAt: string;
}
```

`playerId` must be generated by the backend and must not depend on the player's name.

Player names are display values and must not be used as identifiers.

---

## FR-02 — Supported player age

The application must require a valid age for every player.

For v0.6:

```text
minimum age: 3
maximum age: 99
```

The backend is the authoritative validator.

The frontend may apply the same validation for UX purposes.

---

## FR-03 — List family players

The application must allow the frontend to obtain the available family player profiles.

Endpoint:

```http
GET /players
```

Example response:

```json
{
  "players": [
    {
      "playerId": "player-123",
      "name": "Joaquín",
      "age": 6
    },
    {
      "playerId": "player-456",
      "name": "Amelia",
      "age": 4
    }
  ]
}
```

Ordering should be deterministic.

For v0.6, players should be returned ordered by creation date unless a clearer UI requirement emerges.

---

## FR-04 — Create player profile

The application must allow a family member to create a player.

Endpoint:

```http
POST /players
```

Request:

```json
{
  "name": "Joaquín",
  "age": 6
}
```

Response:

```json
{
  "playerId": "player-123",
  "name": "Joaquín",
  "age": 6,
  "createdAt": "...",
  "updatedAt": "..."
}
```

The backend must:

1. validate the request;
2. normalize leading/trailing whitespace in the name;
3. generate the `playerId`;
4. persist the profile;
5. return the persisted player.

---

## FR-05 — Update player profile

The application must allow changing profile information.

Endpoint:

```http
PUT /players/{playerId}
```

For v0.6 the editable fields are:

```text
name
age
```

The identifier `playerId` must remain immutable.

Changing the age must affect future game generation, but must not modify previously generated games or historical game sessions.

---

## FR-06 — Delete player profile

The application must allow deleting a player profile.

Endpoint:

```http
DELETE /players/{playerId}
```

Deletion of a player must not cascade-delete:

* games;
* generated questions;
* completed game sessions.

Existing historical sessions may preserve their original `playerId`.

For v0.6, hard deletion of the player record is acceptable.

---

## FR-07 — Player selection

The application must present available profiles before starting a player-specific game flow.

Expected high-level flow:

```text
Home
  ↓
Select player
  ↓
Select existing game / Create new game
  ↓
Difficulty / configuration
  ↓
Play
  ↓
Result
```

The selected player must be represented internally by `playerId`, not by player name.

---

## FR-08 — Player-aware game generation

The existing AI game-generation flow must support:

```json
{
  "topic": "Pokémon",
  "difficulty": "easy",
  "questionCount": 10,
  "playerId": "player-123"
}
```

When `playerId` is present, the backend must retrieve the player profile and resolve the player's age before invoking the AI generation service.

The frontend must not be responsible for deriving or sending authoritative age information when a `playerId` exists.

---

## FR-09 — Age-aware AI context

The Application layer must derive an AI generation context from the selected player.

Example:

```ts
interface GameGenerationContext {
  playerId?: string;
  targetAge?: number;
}
```

The AI generator may receive the age as part of the generation request.

Example:

```ts
interface GenerateGameRequest {
  topic: string;
  difficulty: Difficulty;
  questionCount: number;
  targetAge?: number;
}
```

The Bedrock implementation must use `targetAge` to instruct the model to:

* use age-appropriate vocabulary;
* avoid concepts unnecessarily advanced for the player's age;
* adjust question complexity;
* adjust distractor complexity;
* avoid ambiguous questions;
* maintain exactly one correct answer.

---

## FR-10 — Player-aware game sessions

A game session must support association with the selected player.

Example:

```ts
interface GameSession {
  sessionId: string;
  gameId: string;
  playerId?: string;
  ...
}
```

`playerId` remains optional at the domain-contract level when required for backward compatibility with previously created data.

New v0.6 sessions initiated from the main UI should include a player.

---

## FR-11 — Historical integrity

Changes to a player's profile must not retroactively change:

* previously generated games;
* questions;
* answers;
* game-session results.

A game generated for a six-year-old remains the same game even if the player later turns seven or their profile is edited.

---

## FR-12 — Existing game compatibility

Existing games created in v0.3-v0.5 must remain playable.

v0.6 must not require migration of existing `Games` records solely to introduce player profiles.

Existing game IDs and session APIs must remain valid unless explicitly versioned.

---

# 3. Data requirements

A new DynamoDB table must store players.

Logical model:

```text
Players
PK: playerId
```

Example record:

```json
{
  "playerId": "01J...",
  "name": "Joaquín",
  "age": 6,
  "createdAt": "2026-09-11T...",
  "updatedAt": "2026-09-11T..."
}
```

No secondary indexes are required for v0.6.

A table scan is acceptable for the small expected number of family profiles.

The repository abstraction must hide DynamoDB implementation details from Domain and Application.

---

# 4. Application requirements

Introduce a player repository port.

Example:

```ts
interface PlayerRepository {
  list(): Promise<Player[]>;
  getById(playerId: string): Promise<Player | null>;
  create(player: Player): Promise<Player>;
  update(player: Player): Promise<Player>;
  delete(playerId: string): Promise<void>;
}
```

Application use cases must depend on this port rather than on DynamoDB SDK classes.

Example use cases:

```text
ListPlayers
CreatePlayer
UpdatePlayer
DeletePlayer
```

Game generation may depend on `PlayerRepository` to resolve player context.

---

# 5. Infrastructure requirements

Provide a DynamoDB implementation:

```text
DynamoDbPlayerRepository
```

The existing backend Lambda may continue to serve all v0.6 endpoints.

Do not create a new Lambda solely for player management.

The backend Lambda must receive the Players table name through environment configuration.

Example:

```text
PLAYERS_TABLE_NAME
```

IAM permissions must grant only the operations required by the repository.

---

# 6. API requirements

Add:

```http
GET    /players
POST   /players
PUT    /players/{playerId}
DELETE /players/{playerId}
```

Existing APIs must continue to work.

The game-generation endpoint remains:

```http
POST /games/generate
```

but gains player-aware behavior through `playerId`.

No `/v2` API version is required for v0.6.

---

# 7. Frontend requirements

The frontend must provide a simple family-profile experience.

Required capabilities:

* display available players;
* create a player;
* edit a player;
* delete a player;
* select the active player;
* use the active player's `playerId` when generating games;
* use the active player's `playerId` when creating sessions.

The UX must remain appropriate for a family application:

* large interaction targets;
* simple navigation;
* few decisions per screen;
* player names easy to identify.

Complex profile administration is out of scope.

---

# 8. AI privacy requirements

The Bedrock prompt must not receive the player's:

* name;
* `playerId`;
* session identifier;
* application identifiers;
* other personal profile information.

Only the minimum educational context required for generation should be supplied.

For v0.6 this is primarily:

```text
targetAge
```

Example:

```text
Create an educational quiz appropriate for a 6-year-old child...
```

The AI provider must not need to know that the player's name is Joaquín or Amelia.

---

# 9. Validation requirements

Backend validation must reject:

* missing name;
* blank name;
* excessively long name;
* missing age;
* non-integer age;
* age outside the supported range;
* unknown `playerId` when a player is required.

Suggested name limit:

```text
1–50 characters
```

---

# 10. Error handling

Expected application-level conditions should map consistently to HTTP errors.

Examples:

```text
400 INVALID_PLAYER
400 INVALID_PLAYER_AGE
404 PLAYER_NOT_FOUND
409 PLAYER_CONFLICT
```

Infrastructure exceptions must not leak AWS-specific details to the frontend.

---

# 11. Testing requirements

v0.6 must include tests for:

### Domain / Application

* valid player creation;
* invalid age;
* blank name;
* player update;
* player deletion;
* player lookup;
* unknown player;
* game generation resolves player age;
* game generation does not pass player name to the AI provider;
* historical session compatibility.

### Infrastructure

* DynamoDB player repository;
* Players table definition;
* Lambda environment configuration;
* required IAM permissions;
* API routes.

### Frontend

* player list;
* profile creation;
* profile selection;
* profile editing;
* profile deletion;
* generation request uses selected `playerId`.

---

# 12. Non-functional requirements

v0.6 must preserve the existing architectural boundaries:

```text
UI
 ↓
API client
 ↓
HTTP API
 ↓
Lambda / routing
 ↓
Application
 ↓
Ports
 ↓
Infrastructure adapters
```

Domain must remain independent from:

* AWS SDK;
* DynamoDB;
* API Gateway;
* Lambda;
* Bedrock.

No unnecessary new runtime infrastructure should be introduced.

---

# 13. Out of scope

The following capabilities are explicitly outside v0.6:

* authentication per family member;
* individual user accounts;
* Cognito;
* parental-control system;
* profile pictures stored in S3;
* AI-generated avatars;
* PWA installation;
* push notifications;
* offline mode;
* audio;
* images for questions;
* multiplayer;
* real-time synchronization;
* achievements;
* leaderboards;
* sophisticated learning-progress analytics.

These capabilities belong to later phases or future roadmap decisions.

---

# 14. Definition of Done

v0.6 is complete when:

1. players are persisted in DynamoDB;
2. players can be created, listed, edited and deleted;
3. the frontend allows selection of a player;
4. the selected player is associated with new game sessions;
5. `POST /games/generate` accepts a `playerId`;
6. Application resolves the player's age;
7. Bedrock receives age context without receiving the player's identity;
8. generated games continue to pass the existing AI validation pipeline;
9. existing games and sessions remain compatible;
10. infrastructure is deployed successfully;
11. the public application works through the existing Amplify deployment;
12. lint, TypeScript, tests, build and CDK synthesis pass.
