# ADR-012 — Persist family player profiles as a first-class domain entity

## Status

Accepted for v0.6.

## Context

Family Learning Games already contains the concept of a `Player`, but previous versions did not require players to exist as persistent application entities.

This became a limitation once AI-generated games were introduced.

The application needs a stable way to identify the person playing a game and to associate educational characteristics such as age with that player.

Storing the player only in frontend state or static JSON would prevent the backend from using the profile as authoritative context and would not survive different devices or deployments.

Alternatives considered:

1. keep players as frontend-only configuration;
2. embed player information directly in every game session;
3. persist players as independent entities;
4. introduce a complete user/authentication system.

## Decision

Persist `Player` as a first-class domain entity.

Minimum model:

```ts
interface Player {
  playerId: string;
  name: string;
  age: number;
  createdAt: string;
  updatedAt: string;
}
```

Introduce the Application port:

```ts
interface PlayerRepository {
  list(): Promise<Player[]>;
  getById(playerId: string): Promise<Player | null>;
  create(player: Player): Promise<Player>;
  update(player: Player): Promise<Player>;
  delete(playerId: string): Promise<void>;
}
```

Infrastructure implements the port using:

```text
DynamoDbPlayerRepository
```

with a dedicated DynamoDB table:

```text
Players
PK = playerId
```

Player management is exposed through the existing backend and HTTP API.

Routes:

```http
GET    /players
POST   /players
PUT    /players/{playerId}
DELETE /players/{playerId}
```

Do not create a dedicated profile Lambda or microservice in v0.6.

## Rationale

A persistent player entity gives the application a stable identity for gameplay while maintaining separation between:

```text
Player
Game
GameSession
```

A separate DynamoDB table is simpler and cleaner than embedding mutable player attributes in every session.

Using a repository port preserves the architecture established by previous versions:

```text
Application → Port ← Infrastructure
```

A full identity/authentication system would be disproportionate to the v0.6 requirement.

## Consequences

Positive:

* players survive application deployments;
* the backend becomes authoritative for age;
* sessions can be associated with players;
* future personalization has a stable foundation;
* DynamoDB details remain outside Domain and Application.

Trade-offs:

* one additional DynamoDB table;
* additional API endpoints;
* profile lifecycle must be handled explicitly.

## Compatibility

Historical games remain valid.

Historical sessions without `playerId` remain valid.

New v0.6 sessions should normally contain `playerId`.

No migration of existing Games records is required.

## Out of scope

This ADR does not introduce:

* authentication;
* Cognito;
* family accounts;
* PINs;
* passwords;
* profile authorization;
* avatars;
* progress analytics.
