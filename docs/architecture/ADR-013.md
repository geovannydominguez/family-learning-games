# ADR-013 — Derive age-aware AI personalization from player profiles

## Status

Accepted for v0.6.

## Context

v0.4 introduced AI-generated games through the provider-neutral port:

```ts
interface GameGenerator {
  generate(request: GenerateGameRequest): Promise<GeneratedGameDraft>;
}
```

The infrastructure implementation uses Amazon Bedrock.

The project has already observed that semantic correctness and age suitability are important for generated content.

Difficulty alone is not enough to determine age appropriateness.

For example:

```text
difficulty = hard
```

does not answer whether the game is intended for:

```text
a 6-year-old
or
an adult.
```

At the same time, the AI provider does not require the identity of the family member.

Sending player names or identifiers to Bedrock would unnecessarily couple AI generation with personal profile data.

## Decision

When a game-generation request contains:

```text
playerId
```

the Application layer must resolve the player through `PlayerRepository`.

Example:

```text
playerId
   ↓
PlayerRepository
   ↓
Player.age
   ↓
targetAge
   ↓
GameGenerator
```

The `GameGenerator` request may therefore contain:

```ts
interface GenerateGameRequest {
  topic: string;
  difficulty: Difficulty;
  questionCount: number;
  targetAge?: number;
}
```

The AI adapter receives:

```text
targetAge
```

but must not receive:

```text
playerId
player name
sessionId
family metadata
```

`difficulty` remains independent from `targetAge`.

The generator and validator must interpret difficulty relative to the target age.

## Example

Input from frontend:

```json
{
  "topic": "Pokémon",
  "difficulty": "hard",
  "questionCount": 10,
  "playerId": "player-123"
}
```

Application resolves:

```json
{
  "playerId": "player-123",
  "name": "Joaquín",
  "age": 6
}
```

Input to AI boundary:

```json
{
  "topic": "Pokémon",
  "difficulty": "hard",
  "questionCount": 10,
  "targetAge": 6
}
```

The player's name and ID do not cross the AI boundary.

## Rationale

This applies data minimization while giving the model the information required for educational personalization.

It also keeps responsibilities clear:

```text
Frontend
selects player

Application
resolves player context

GameGenerator
works with educational generation parameters

Bedrock adapter
translates those parameters into model instructions
```

The AI adapter therefore remains independent of the family-profile model.

## Historical behavior

Generated content must not depend on the player's current profile after generation.

If useful for traceability, the generated game may persist:

```ts
generationMetadata: {
  targetAge: 6,
  difficulty: "hard"
}
```

A later player age update must not mutate existing games.

## Consequences

Positive:

* substantially better age-aware generation;
* no player identity sent to Bedrock;
* `GameGenerator` remains provider-neutral;
* profile edits do not alter historical games;
* future AI providers can use the same application contract.

Trade-offs:

* game generation requires a player lookup;
* age becomes an additional generation variable;
* AI tests must cover both age and difficulty.

## Security and privacy

Only the minimum educational context should cross the AI boundary.

Allowed:

```text
topic
difficulty
questionCount
targetAge
```

Not allowed:

```text
playerId
name
sessionId
family relationship
other personal profile attributes
```

This rule should be enforced in tests.

## Out of scope

This ADR does not define:

* long-term learning history;
* adaptive difficulty based on previous answers;
* AI-generated psychological or educational profiles;
* recommendations based on behavioral analytics;
* personalization across families.

Those capabilities require separate product and architecture decisions.
